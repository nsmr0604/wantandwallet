# 1. 目的

開発の過程（判断・設計・変更・検証）を**常に**残し、後から読める形にする。図は文章より速く伝わるため、構造・流れ・状態は UML で表す。

**原則**

1. **決定は理由つきで残す**（ADR）。「何をしたか」ではなく「なぜそうしたか」
2. **図はコードで管理する**（Mermaid）。画像を貼らず、差分でレビューできる状態を保つ
3. **ID で相互参照する**（`R-xx` 要件 / `D-xx` 決定 / `K-xx` リスク / `Q-xx` 未決 / `S<n>` スパイラル）
4. **変更したら同じコミットで文書を直す**。実装だけ進めて文書が遅れる状態を作らない

# 4. UML の使い分け

| 知りたいこと | 図 | Mermaid |
| --- | --- | --- |
| 誰が何のために使うか | ユースケース図 | `flowchart` / `mindmap` |
| 画面や状態がどう移るか | 状態遷移図 | `stateDiagram-v2` |
| 処理の順番・分岐 | アクティビティ図 | `flowchart` |
| 外部とのやり取りの時系列 | シーケンス図 | `sequenceDiagram` |
| データの構造と関連 | ER 図 | `erDiagram` |
| クラス・型の関係 | クラス図 | `classDiagram` |
| システムの構成要素 | C4 コンポーネント図 | `flowchart`（subgraph） |
| スケジュール | ガントチャート | `gantt` |

## 4.1 Mermaid を書くときのルール

- **1 図 1 目的**。詰め込まず、必要なら分割する
- 図の直前に「何を表す図か」を 1 文で書く
- ノード名は日本語可。ID は英数字（`A[欲しいリスト]`）
- 色分けは意味を持つ場合のみ（最安・警告・予約中など）
- 破線は「任意・将来（C 要件）」、実線は「MVP の動作」を表す

# 5. ADR の書き方（05 に追記）

```md
| D-xx | 日付 | 決定（1 文） | 理由（なぜ・代替案との比較） |
```

- 覆した決定は消さずに「**superseded by D-yy**」と注記する
- 影響が要件・データ・画面に及ぶ場合は、同じコミットで各 doc を更新する

# 6. ユースケース記述の型（01 に追記）

```md
### UC-xx 名称
- アクター: 
- 目的: 
- 事前条件: 
- 基本フロー: 1. … 2. …
- 代替/例外: 
- 事後条件: 
- 関連: R-xx, D-xx
```

# 7. 更新の義務（Definition of Documentation）

次のいずれかに該当したら、**同じコミット**で文書を更新する。

- [ ] 要件の追加・変更・削除 → `01`（受入基準も）
- [ ] データ構造・計算の変更 → `03`（ER 図・スキーマ・計算表）
- [ ] 技術・ライブラリ・配信の変更 → `02`（C4 図・選定理由）
- [ ] スコープ・順序・期日の変更 → `04`（ガント・DoD）
- [ ] 判断をした → `05`（ADR）＋未決事項の更新
- [ ] 画面・導線の変更 → `07`（状態遷移図・ワイヤー）
- [ ] 新しいリスク・指標 → `06`（K-xx・指標表）

# 8. レビュー観点（文書自体の品質）

1. 初見の人が「なぜ」まで理解できるか（理由が書かれているか）
2. 図と本文が矛盾していないか
3. ID 参照が切れていないか（`R-xx` などが実在するか）
4. 用語が `01` §7 の用語集と一致しているか
5. 更新日と `version` が上がっているか
